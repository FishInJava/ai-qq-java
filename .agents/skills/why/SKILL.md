# 动机追溯

查代码背后的动机与意图。`how` 回答代码做什么、怎么运作，`why` 回答是什么力量把它塑造成现在这样。

证据只有两处：代码库本身，以及 PR 与提交记录。工单、聊天、监控这些外部来源不在范围内。查不到就写进缺口，不要拿推测补。

## 谁能跑

	主对话可以直接用。work-work 的 playbook-agent 也能用，它不能开子代理，自己顺序跑。

	需要并行时用当前 harness 的通用子代理。模型按用户配置来，没配置就继承主对话。

## 第 1 步 定位

	先确定查哪段代码，别急着翻历史。

	记下文件路径与行号、关键符号（函数、类、常量），以及这段代码在系统里的位置。

	拿到种子提交：

		git log --oneline -20 -- <file>
		git blame -L <start>,<end> <file>
		git show <hash>

	提交标题里有 `(#1234)` 就是 PR 号。有 `gh` 且已登录时读 PR 正文与讨论：

		gh pr view <n> --json title,body,author,createdAt,mergedAt,comments,reviews

## 第 2 步 取证

	先只收集，不下判断。每条记下出处。

	- 提交信息：说了什么，有没有写原因。
	- PR 正文与评审评论：设计理由最常出现在这里。
	- 代码注释：尤其是解释「为什么这么写」的注释。
	- 测试：测试名和断言常记录了促成改动的边界情况。
	- `.agents/notes/` 决策笔记：一个决定一个文件，Problem 与 Alternatives 两节就是理由。
	- `AGENTS.md` 与 `RULES.md`：项目约束，能解释某些看起来奇怪的写法。
	- 同一次提交里一起改动的文件：共变信号，说明这次改动牵动了什么。

	命令与细节见 `references/code-archaeology.md`。

	查完先把证据列成清单，每条写清它说了什么、出处、与问题的关系。写到这一步还不要下结论。

## 第 3 步 写

	按下面的结构写，用不上的节删掉。

### 问题
	一到两句复述用户的问题。

### 查到了什么
	每条带出处和档位标记。

	- **[直接]** {结论}。来源：PR #123 / 提交 abc1234 / 文件:行号。{简短引用或转述。}
	- **[支持]** {结论}。证据：{逐条列出材料，以及每条贡献了什么}。

### 可以合理推断
	没有明说、但被间接证据充分支持的结论。每条把推理链写出来，用带保留的措辞。没有就删掉这一节。

### 还不知道什么
	写具体缺口：查了什么、在哪查的、结果是什么。确实没有缺口时，写清查过哪些地方，不要留空。

### 可信度小结
	一到两句，说清哪些是查到的、哪些是推断的、哪些没查到。

### 涉及的代码
	问题涉及的文件与符号不明显时加这一节，两三行。

### 竞争假设
	证据能撑起多个故事时加这一节，每条写假设、支持证据、反对或缺失的证据。

## 硬规则

	- 直接或支持档的结论必须带引用，推断只用带保留的措辞。
	- 代码本身不能当作它自己意图的证据。提交改了什么，不等于说明了为什么。
	- 置信分层与措辞要求见 `references/epistemics.md`，动笔前读一遍。
