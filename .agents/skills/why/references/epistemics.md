# 置信分级

历史证据往往残缺、互相矛盾，有时根本不存在。这一节规定怎么在这种材料上判断可信度，以及怎么讲给用户而不压成假的确定结论。代码只说明它做什么，不说明它为什么存在。动机藏在提交、PR、代码注释和决策笔记里，这些材料都不完整、有偏差，有时干脆没有。装出把握，产出的就是听起来笃定的猜测，会误导用户。

## 置信分级

输出里的每条结论必须落在其中一档。档位决定它进哪一节，以及用什么措辞。

### 1. 直接

有一段明确的文字引用直接回答了问题，作者真的写下了为什么，而不是「代码在做 X，所以作者大概想要 X」。例如 PR 正文写着「这修的是用户条目超过 1000 条时无法翻页的问题」，代码注释写着「截到 100，因为上游 API 拒绝更大的值」，决策笔记写着「选 A 不选 B，因为需要重启后仍然保留」，或者评审评论里写着「换成这个做法，旧的测试里不稳定」。

措辞：肯定、现在时、带引用。写成「这个存在是因为 X。」

### 2. 支持

多条间接证据指向同一个结论。没有任何一条来源直接这么说，但把几条拼起来，这个结论很可能成立。例如 PR 标题写「改进性能」，同期相关提交都在动同一段热点代码。或者随改动新增的几个测试都在跑超大输入。或者同一周的其他 PR 都提到同一次故障。

措辞：肯定，但明确写出是推出来的，并逐条引用。「证据强烈指向 X，具体是这几条……」。

### 3. 推断

对上下文的一种合理解读，没有任何材料明确支持。这是你的解释，不是记录里的事实。例如 PR 没写原因，但同一周有多次紧急修复的提交，这次又当天就合了，那它大概是热修。或者函数名看起来像重试逻辑，重试次数 3 又和仓库里别处的 3 次重试惯例一致。

措辞：带保留，把推理链写出来。「有 A 和 B 这两点，C 看起来可能成立，因为 D。」

### 4. 推测

在很薄的证据上提出的合理假设，其他解释同样说得通。值得写出来，因为用户可能知道哪个对，但要标明这是猜的。例如「这可能是绕开一个后来已经修掉的浏览器 bug，但我们没找到当时的证据」，或者「这个阈值可能是在对齐某个 SLA 承诺，但没有文档提到它」。

措辞：「一种可能是 X，但我们没有直接证据。」通常放在「竞争假设」一节，和其他可能并列。

### 5. 未知

查过了，没查出来。这是一个有效且重要的结果，要写下来。

措辞：「我们查了 X、Y、Z，没有找到为什么。」要把查过什么写具体。「查不出来」远不如「用 git log 搜了关键词 A 和 B，翻了 2023 年以来碰过这个文件的 6 个提交，又在仓库里 grep 了和这个阈值匹配的字面量，都没有出现理由」。

## 措辞规范

**表示确信的词**意味着直接或支持档证据，旁边必须紧跟引用。推断绝不能用这些词：「因为」「原因是」「是为了」（都在断言作者意图）、「修复了」「解决了」（都在断言改动达到了目的）、「团队决定」（都在断言发生过一次集体决策）。

**带保留的词**表示这是解读，不是记录。在「可以合理推断」一节里大量使用：「看起来」「似乎」「可能」「说明有可能」「与……一致」「一种读法是」「说得通」「也许是」「证据指向」。

**避免用的词：**

- 「显然」。真的显然，用户就不会问了
- 「很明显」。后面跟的往往是不明显的话
- 「当然」。同上
- 「只是」。例如「这只是为了性能」，带轻慢，通常在掩盖不确定
- 「我认为」「我相信」。你在综合证据，不是在发表个人意见。用「证据表明」代替

## 不要事后编理由

今天看起来「说得通」的代码，可能是为了已经不存在的原因写的，也可能当时就是错的。不要给混乱的历史补一个干净的理由。不要假设作者做的是「对的事」，再倒推去证明它。不要因为某处呈现出规律就认定那是有意为之，它可能是复制粘贴。也不要把「没有证据」变成「证明没有」。「没人提过安全顾虑，所以当时不考虑安全」就是这种错误。

## 迎合陷阱

用户常在问题里夹带一个假设。「我们为什么这么做，我猜是为了性能？」不要顺着确认。这个猜测是调查的线索，不是要验证的结论。把它当成候选之一，独立查证据。证据支持就这样说，并给引用。证据不支持也直说，然后给出证据真正支持的东西。

## 证据互相矛盾时

把两边都摆出来，各自带引用。不要挑更顺故事的那条。例如 PR 说「这是客户 X 的合规要求」，同一个提交的评审评论说「顺手清理这块技术债」。两者都可能为真，一个说动因，一个说做法，也可能有一个是错的。让用户自己判断。

## 证据缺失时

一句诚实的「不知道」是最有价值的输出之一。用户会知道答案不在显眼的地方，需要去问人（原作者、产品负责人、组长），或者可以判断这个问题不值得继续追。漏标一个缺口，用笃定的猜测填上，会实实在在害到用户，因为他会照着这个猜测行动。每个缺口都要写具体：问题是什么、查过哪些来源、在每个来源里搜了什么、结果是什么（什么都没有，只有边缘材料）。

## 定稿之前

合成者交付之前逐条检查「我们查到了什么」和「可以合理推断」里的每条结论。每条要么带引用，要么挪到推断或假设。措辞要和档位匹配。代码不能当作它自己意图的证据，出现了就删掉或重新归类。输出里必须有「还不知道什么」一节。一个缺口都没提反而可疑，要么证据确实异常完整，要么有人在掩盖。
