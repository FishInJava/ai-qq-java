# 怎么运作

回答「X 怎么运作」。产出写给资深工程师的架构解释，够他建立能直接干活的心智模型，不需要细节到每行源码。

## 1. 判定复杂度

	范围含糊时先说明你的理解再动手，用户可以纠正。

	- 简单：单个模块、一个小工具，或「函数 X 怎么走」这种窄问题。不开explorer，一个explainer边读边解释，从 `references/explainer-prompt.md` 建提示词，直接跳到第 4.交付。
	- 复杂：跨多文件或多服务的子系统、横切功能、整体架构概览。走第 2 步。

	拿不准时按简单处理。

## 2. 探索（仅复杂场景）

	把问题拆成 2 到 4 个角度，每个角度是一块不同的子系统切片。能并行就把探索者一次全派出去，每个都带 `references/explorer-prompt.md` 和填好的角度。

## 3. 合成（仅复杂场景）

	探索者都回来后，派一个解释者，带 `references/explainer-prompt.md` 和所有探索结果。

## 4.交付

	直接给解释者的输出。按对话上下文做轻微修改可以，不要大改。

## 输出格式

	用 `references/explainer-prompt.md` 定义的节，用不上的删掉：概述、关键概念、运作方式、代码位置、易错点。
