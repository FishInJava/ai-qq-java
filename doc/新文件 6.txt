【DSH源码】
	1.Loop核心
	messages = [system_prompt, user_input]
	loop:
		response = LLM(messages, tools)
		if response 有 tool_call:
			result = 执行 tool_call
			messages.append(result)
			continue          # 继续转
		else:
			return response   # 没有工具调用 = 说完了 = 退出
	注意：除了不再tool_call，还有一种主动退出方式：人退出 + step/时间/token达到上限。
	
	2.状态机:5种
	idle/created  初始，还没跑 next -> running
	running/working 循环里 next -> idle(跑完了)，waiting(要人工)，error
	waiting/blocked 卡住等人:确认/补参数 next-> running
	idle  跑完了一轮，输入后继续跑 next-> running
	error/terminated 终态 ，不能next了
	
	3.5个动词：
	create/spawn  开启一个Agent
	send/continue 追加消息，通常就
	interrupt 停止这轮
	inspect/list 查询:状态，看树
	kill/terminate 销毁，回收资源。
	
	4.工具层：Agent探索世界
	Agent只会2种话：文本和tool_call。
	有3种tool_call的挂载方法：
		-函数调用：不是系统调用，我以为是OS的。 CLI指令就属于函数调用。
		-代码执行：
		-MCP
	
	5.多Agent的3种拓扑
		-Leader-Worker
		-接力/路由：A判断该谁干，就把控制权交给谁
		-群聊
	注意：这里有2个独立维度。维度一：控制关系，父->子。 维度二:执行实体 进程->进程。
		比如，父子 + 同进程，用subAgent实现，同进程中的2个不同Session。
		Leader-Worker可以派一个跑在远端机器上的 worker。
	单进程多Session：最常见。共享内存、共享文件系统。
	多进程： 缺点：通信要序列化，状态不能共享内存，得走 IPC / 文件 / socket。
	跨机器：分布式系统。网络分区、重试、幂等、一致性。
	
	建议：你之前准备做 subAgent管理，先确定维度二，再确定维度一。
		-第一版肯定是所有进程都在一个OS上。
	
	父子说的是“谁派的活”，跨进程说的是“在哪跑”。我讲的三种拓扑是前者，你担心的“状态/隔离/恢复”是后者。
	
	6.上下文

		-外部记忆
		-结构化返回/传递
	
	7.其他：观测/可视化，安全/权限(沙箱，白名单)

【MCP】目前还真有一个codegraph【这种东西要证明他有用，最好就是Hook去观察他】
	MCP不是模型决定调用的，而是Agent用的。
		-模型只通过tool和Agent交互。通常是：模型->Agent（tool_call）->MCP
		-MCP：Model Context Protocol，和模型有个JB关系，就是一个JSON-RPC协议
		-此时Agent作为Client，通过json-RPC协议，访问外界MCP-Server，获取某些信息

	另一种和外界交互的能力：CLI，比如github提供cli，模型感知后，直接通过tool_call -> shell -> github
	协议是任意的，可以是http。
	这种模型是通过 --help指令现学的。
